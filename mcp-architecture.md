# MCP Server Architecture

Model Context Protocol (MCP) server for external clients (opencode, Cursor, Claude Desktop, etc.) to authenticate as a JoblyAI user and invoke tools against their data. Built on the official `@modelcontextprotocol/sdk` Streamable HTTP transport with **Bearer API-key authentication** via Better-Auth's `apiKey` plugin.

The server is **stateless** — every request creates a fresh `StreamableHTTPServerTransport` and `McpServer`, handles the request, and lets them garbage-collect. No `sessionIdGenerator` is passed, so there is no `Mcp-Session-Id` round-trip. Any backend instance can handle any request, and horizontal scaling requires no shared state.

```
v1 scope: foundation + whoami tool + API-key CRUD.
v2 scope: role-gated API keys + employer tools (read + write), one file per tool.
v3 scope: candidate tools (7 tools: search, apply, list applications, withdraw, profile, list resumes, update profile) — mirrors web's createApplication for apply_to_job with match-explanation + notifications + event emission.
v4+ scope: AI-only tools, messaging, cross-role tools, resume upload.
```

**Role gating:** every MCP key carries a single role (`employer` or `candidate`) stored in Better-Auth's `apikey.permissions` JSON column. The `ApiKeyGuard` reads it on every request, the `McpEndpointController` resolves the caller's `companyId` (for `employer` keys), and the `McpFactory` conditionally registers tool groups based on the role. v2 ships employer tools (9); v3 adds candidate tools (7) — candidate keys now get a full tool set.

## 1. Data Model

### Apikey table (PostgreSQL via Prisma)

`apps/backend/prisma/schema.prisma:554-582` — generated by Better-Auth's `apiKey` plugin, mapped to the `apikey` table:

```prisma
model Apikey {
  id                  String    @id
  configId            String    @default("default")
  name                String?
  start               String?
  referenceId         String      // ← user id (Better-Auth convention)
  prefix              String?
  key                 String      // ← bcrypt-hashed; plaintext is never stored
  refillInterval      Int?
  refillAmount        Int?
  lastRefillAt        DateTime?
  enabled             Boolean?  @default(true)
  rateLimitEnabled    Boolean?  @default(true)
  rateLimitTimeWindow Int?      @default(86400000)
  rateLimitMax        Int?      @default(10)
  requestCount        Int?      @default(0)
  remaining           Int?
  lastRequest         DateTime?
  expiresAt           DateTime?
  createdAt           DateTime
  updatedAt           DateTime
  permissions         String?
  metadata            String?

  @@index([configId])
  @@index([referenceId])
  @@index([key])
  @@map("apikey")
}
```

**Indexes** are auto-generated by `pnpm auth:schema`:

- `referenceId` — list keys for a user (`listApiKeys`)
- `key` — point lookup on `verifyApiKey` (hash-and-compare path)
- `configId` — plugin internal

**Key shape:** plaintext (e.g. `jobly_sk_aB3xY...`) is shown to the user exactly once on `POST /api/mcp-keys`. The DB stores the bcrypt hash. The `prefix` is kept verbatim for display/identification; the `start` column stores the first 6 characters (Better-Auth's `startingCharactersConfig.charactersLength` default) so the UI can show partial keys without revealing them.

**Per-key rate-limit fields** (`rateLimitMax` / `rateLimitTimeWindow` / `rateLimitEnabled`) are baked in at creation time from the plugin config (see §3). Updating the plugin config does **not** affect existing keys — to change a key's limits, the user must delete and recreate it.

**`permissions` column** (`String?`, JSON-encoded `Record<string, string[]>`) — set at key creation via `auth.api.createApiKey({ body: { ..., permissions: { role: ['employer'] } } })`. v2 stores a single key `role` with one-element array `['employer' | 'candidate']`. The `ApiKeyGuard` parses it on every request and rejects keys without a valid role (see §3a).

## 2. Better-Auth `apiKey` plugin config

`apps/backend/src/lib/auth.ts:94-103`:

```ts
apiKey({
  defaultPrefix: 'jobly_sk_',
  defaultKeyLength: 32,
  storage: 'database',
  rateLimit: {
    enabled: true,
    timeWindow: 60 * 1000,    // 1 minute
    maxRequests: 1000,        // 1000 req/min/key
  },
}),
```

| Option                  | Value         | Notes                                                                  |
| ----------------------- | ------------- | ---------------------------------------------------------------------- |
| `defaultPrefix`         | `'jobly_sk_'` | Plausible-looking prefix for grep-ability and accidental-paste safety. |
| `defaultKeyLength`      | `32`          | Random body length (excluding prefix).                                 |
| `storage`               | `'database'`  | Hashes keys server-side; persists to the `apikey` table.               |
| `rateLimit.enabled`     | `true`        | Disable-able per-key via `rateLimitEnabled` field.                     |
| `rateLimit.timeWindow`  | `60_000`      | Sliding 1-minute window.                                               |
| `rateLimit.maxRequests` | `1000`        | 1000 requests per minute per key.                                      |

**Why 1000/min:** Better-Auth's default is `10 requests per 24 hours` (`node_modules/@better-auth/api-key/dist/index.mjs:2286-2289`) — an MCP server with opencode makes multiple sub-requests per session (`initialize` → `tools/list` → many `tools/call` for an agent loop), and 10/24h gets exhausted by 1-2 sessions. 1000/min still rate-limits (defense against compromised-key abuse) but never breaks a real workflow.

**Plugin package:** `apiKey` is imported from `@better-auth/api-key@1.6.19` (NOT from `better-auth/plugins`). The version is pinned to match the installed `better-auth@1.6.19`.

**Per-key override at creation:** the service could pass `rateLimitMax` / `rateLimitTimeWindow` to `auth.api.createApiKey`, but the v2 service uses the plugin defaults and passes `name` + `permissions` from the DTO (see §4).

## 3. Authentication

Two independent auth surfaces, both routed through the same NestJS module:

### 3a. Bearer API key (MCP endpoint)

`apps/backend/src/app/mcp/auth/api-key.guard.ts` — `ApiKeyGuard.canActivate`:

```
1. Read `Authorization` header
   - absent                        → 401 missing_api_key
   - not "Bearer …"                → 401 invalid_authorization_header
2. Slice off "Bearer " → key
3. await auth.api.verifyApiKey({ body: { key } })
4. !result.valid                  → 401 invalid_api_key
5. !result.key?.referenceId       → 500 key_misconfigured
6. Parse result.key.permissions   → read .role[0]
   - missing / not 1 element      → 401 role_not_set
   - value not in {employer, candidate} → 401 invalid_role
7. request.mcpUserId = result.key.referenceId
8. request.mcpRole  = role
9. return true
```

**Every 401** (missing, malformed, invalid) sets `WWW-Authenticate: Bearer realm="jobly-mcp"` on the response (RFC 6750 §3). This tells well-behaved clients to use Bearer auth, not OAuth — eliminating noisy OAuth discovery probes (`/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/.well-known/openid-configuration`, `POST /register`) when opencode falls back to discovery after a 401.

**Verify error mapping** (no-guard state):

| `verifyApiKey` outcome                                        | Response                                  |
| ------------------------------------------------------------- | ----------------------------------------- |
| `result.valid === false`                                      | 401 `invalid_api_key`                     |
| `result.key?.referenceId` is `null`/`undefined`               | 500 `key_misconfigured`                   |
| `result.key.permissions` missing / `role` not 1-element array | 401 `role_not_set`                        |
| `permissions.role[0]` not in `{employer, candidate}`          | 401 `invalid_role`                        |
| `verifyApiKey` throws (DB error, etc.)                        | unhandled — bubbles to Nest's default 500 |

**Rate-limit behavior:** if a key has already exceeded its per-key limit, `verifyApiKey` returns `{ valid: false, error: { code: 'RATE_LIMITED' } }` — mapped to 401 `invalid_api_key`. The library throws a separate `APIError` with statusCode 429 in some versions; in that case the call bubbles and Nest returns 500. The first behavior is the one we observe with `@better-auth/api-key@1.6.19`.

### 3b. Better-Auth session cookie (key management endpoints)

`apps/backend/src/app/mcp/keys/mcp-keys.controller.ts` — `@UseGuards(AuthGuard)` from `apps/backend/src/app/auth/auth.guard.ts`. The session cookie (`better-auth.session_token`, HTTP-only) is set by the standard auth flow (`POST /api/auth/sign-in/email`) and the `AuthGuard` validates it before any controller method runs. `AuthenticatedRequest.user.id` is the source of `userId` for `McpKeysService.create`.

This is the SAME `AuthGuard` used everywhere else in the app — the MCP module does not own session validation.

### 3c. `RequestWithMcpUser` type

`apps/backend/src/app/mcp/auth/api-key.types.ts:3-5`:

```ts
export interface RequestWithMcpUser extends Request {
  mcpUserId?: string;
  mcpRole?: 'employer' | 'candidate';
}
```

Both `mcpUserId` and `mcpRole` are attached by `ApiKeyGuard` after successful verification. The `McpEndpointController` reads them on the same request (`mcp-endpoint.controller.ts:29`):

```ts
if (!req.mcpUserId || !req.mcpRole) {
  this.logger.error('mcpUserId or mcpRole missing on request after guard');
  if (!res.headersSent) res.status(500).json({ error: 'internal_error' });
  return;
}
```

This is a **defensive guard** (avoids `@typescript-eslint/no-non-null-assertion`). The guard always sets both on success, so this branch is unreachable in practice — but it protects against future guard refactors that might forget the assignment.

## 4. REST API — key management

`apps/backend/src/app/mcp/keys/` — three endpoints, all under `/api/mcp-keys`, all session-protected:

| Method   | Endpoint            | Body              | Returns                                      |
| -------- | ------------------- | ----------------- | -------------------------------------------- |
| `POST`   | `/api/mcp-keys`     | `CreateMcpKeyDto` | `CreateMcpKeyResponse` (with one-time `key`) |
| `GET`    | `/api/mcp-keys`     | —                 | `McpKeyView[]`                               |
| `DELETE` | `/api/mcp-keys/:id` | —                 | `204 No Content`                             |

`POST` body schema (`apps/backend/src/app/mcp/keys/dto/create-mcp-key.dto.ts`):

```ts
class CreateMcpKeyDto {
  @IsIn(['employer', 'candidate'])
  role!: 'employer' | 'candidate';

  @IsString()
  name!: string;
}
```

The role is **mandatory** and gates the entire key. One user may have one key per role (no DB-level enforcement yet — duplicate keys are accepted; the user is expected to delete the old one).

### View DTOs

`apps/backend/src/app/mcp/keys/dto/mcp-key.view.ts`:

```ts
export interface McpKeyView {
  id: string;
  name: string;
  prefix: string;
  createdAt: Date;
  lastRequest: Date | null;
  expiresAt: Date | null;
  role: 'employer' | 'candidate' | null;
}

export interface CreateMcpKeyResponse extends McpKeyView {
  key: string; // ← plaintext; one-time only
}
```

`role` is parsed from the key's stored `permissions` JSON (`permissions.role[0]`); `null` for malformed or missing role data.

**Field-name note:** the DB column is `lastRequest` (not `lastUsedAt` as the spec originally said). The view DTO uses the actual DB field.

### Service implementation

`mcp-keys.service.ts` — thin wrapper over Better-Auth's `auth.api`:

```ts
async create(userId: string, dto: CreateMcpKeyDto): Promise<CreateMcpKeyResponse> {
  const result = await auth.api.createApiKey({
    body: { userId, name: dto.name, permissions: { role: [dto.role] } },
  });
  return { id, key, prefix, name, createdAt, lastRequest, expiresAt, role: dto.role };
}

async list(headers): Promise<McpKeyView[]> {
  const { apiKeys } = await auth.api.listApiKeys({ headers });
  return apiKeys.map(key => {
    const role = (key.permissions as { role?: string[] } | null)?.role?.[0];
    return { /* ... */, role: role === 'employer' || role === 'candidate' ? role : null };
  });
}

async delete(keyId: string): Promise<void> {
  await auth.api.deleteApiKey({ body: { keyId } });
}
```

**`createApiKey` permissions:** passed as `permissions: { role: [dto.role] }` — a single-element array under the `role` key. The `ApiKeyGuard` expects exactly this shape (see §3a).

**`listApiKeys` return shape** (`@better-auth/api-key@1.6.19`): `{ apiKeys: [...], total, limit, offset }` — the service destructures `apiKeys`. An earlier draft of the spec assumed a raw array; that was wrong.

**`headers` for `listApiKeys`:** the service receives `{ authorization: req.headers.authorization }` from the controller. Better-Auth re-validates the session against the header (cookie also works, but passing the header keeps the call consistent with the REST shape).

**Caveat:** `list` and `delete` operate on the **current session's user**. `listApiKeys` returns all keys where `referenceId === currentUser.id`. `deleteApiKey` checks the same ownership server-side. A user cannot delete another user's key.

## 5. MCP endpoint (Streamable HTTP)

`apps/backend/src/app/mcp/server/mcp-endpoint.controller.ts` — 4 constructor DI params (`PrismaClient`, `MatchExplanationService`, `EventEmitter2`, `NotificationsService`), single `@All()` handler on `/api/mcp`, guarded by `ApiKeyGuard`:

```ts
@UseGuards(ApiKeyGuard)
async handleMcp(@Req() req: RequestWithMcpUser, @Res() res: Response): Promise<void> {
  if (!req.mcpUserId || !req.mcpRole) { /* defensive 500 */ return; }
  const userId = req.mcpUserId;
  const role = req.mcpRole;

  // 1. Resolve companyId for employer keys (single per-request DB lookup)
  const employer = await this.prisma.employer.findUnique({
    where: { employerId: userId },
    select: { companyId: true },
  });

  // 2. Create per-request transport — stateless, no sessionIdGenerator
  const transport = new StreamableHTTPServerTransport({
    sessionIdGenerator: undefined,
  });

  // 3. Create per-request McpServer with caller-scoped state
  const server = createMcpServer({
    userId,
    role,
    companyId: employer?.companyId ?? null,
    prisma: this.prisma,
    logger: this.logger,
    matchExplanationService: this.matchExplanationService,
    eventEmitter: this.eventEmitter,
    notificationsService: this.notificationsService,
  });

  // 4. Wire transport to server
  await server.connect(transport);

  // 5. Cleanup on response close (idle timeout, disconnect, error)
  res.on('close', () => {
    void transport.close();
    void server.close();
  });

  // 6. Handle the JSON-RPC message
  try {
    await transport.handleRequest(req, res, req.body);
  } catch (err) {
    this.logger.error({ err, userId }, 'mcp.handleRequest failed');
    if (!res.headersSent) {
      res.status(500).json({ error: 'internal_error' });
    }
  }
}
```

**Why stateless:** passing `sessionIdGenerator: undefined` tells the SDK transport to skip session ID generation and the `Mcp-Session-Id` round-trip. The MCP spec supports this mode (`streamableHttp`) for clients that can re-authenticate on every request. The trade-off:

|                                    | Stateful (default)                      | Stateless (our choice)     |
| ---------------------------------- | --------------------------------------- | -------------------------- |
| Per-request overhead               | Reuse transport/server                  | Create + GC per request    |
| `Mcp-Session-Id` header round-trip | Required                                | Skipped                    |
| Horizontal scaling                 | Requires sticky sessions / shared state | Any instance → any request |
| Server-side session cleanup        | Required (TTL, eviction)                | None                       |

The user confirmed stateless is permanent: "we will never go stateful."

**Why per-request `McpServer`:** state (userId, prisma) is per-caller. Creating a fresh server per request guarantees no state leaks between concurrent users sharing a Node process. The cost is construction overhead — negligible compared to the JSON-RPC round-trip.

**`res.on('close')` cleanup:** fires on client disconnect, response stream close, or HTTP keep-alive timeout. `transport.close()` and `server.close()` release internal resources (in-flight `tools/call` cancellations, event listener cleanup).

**Error handling:** the `try/catch` around `transport.handleRequest` logs the error with the userId context and returns a 500 if the response hasn't been written. The MCP SDK's `StreamableHTTPServerTransport` may also write a JSON-RPC error frame directly to `res` — in that case `res.headersSent` is true and we don't double-write.

## 6. Tools — the whoami pattern

`apps/backend/src/app/mcp/tools/whoami.tool.ts` — the pattern every v2+ tool will follow:

```ts
// 1. Pure handler — testable in isolation
export async function whoamiHandler(state: McpState) {
  try {
    const user = await state.prisma.user.findUnique({
      where: { id: state.userId },
      include: { employer: true, candidateDescription: true, resumes: true },
    });
    if (!user)
      return {
        isError: true,
        content: [{ type: 'text', text: 'User not found' }],
      };

    const result = {
      id: user.id,
      email: user.email,
      name: `${user.firstName ?? ''} ${user.lastName ?? ''}`.trim(),
      role: user.role ?? 'candidate',
      hasCandidateProfile:
        !!user.candidateDescription || user.resumes.length > 0,
      hasEmployerProfile: !!user.employer,
    };
    return {
      content: [{ type: 'text', text: JSON.stringify(result, null, 2) }],
      structuredContent: result,
    };
  } catch (error) {
    state.logger.error(error, 'whoami tool error');
    return {
      isError: true,
      content: [{ type: 'text', text: 'Internal error' }],
    };
  }
}

// 2. Thin registration wrapper — trusted without a dedicated test
export function registerWhoamiTool(server: McpServer, state: McpState): void {
  server.registerTool(
    'whoami',
    {
      description: 'Get the current user profile',
      inputSchema: z.object({}),
      outputSchema: z.object({
        /* same shape as result */
      }),
      annotations: { readOnlyHint: true, openWorldHint: false },
    },
    async () => whoamiHandler(state)
  );
}
```

**Why two exports:** the MCP SDK's `McpServer` class does not expose `callTool` / `listTools` as public methods — those are methods on the **client** (`Client` class), not the server. There is no `server.callTool('whoami', {})` to test against. Without `whoamiHandler` extracted, the only way to test the logic would be to spin up a real Streamable HTTP transport and call it from a real MCP client — slow and brittle.

`whoamiHandler` is the testable seam. The test imports it and calls it with a mock `McpState` (mock `prisma.user.findUnique`, real `logger` or stub). `registerWhoamiTool` is a 2-line wrapper that we trust without a dedicated test.

**Tool errors:** returned as `{ isError: true, content: [{ type: 'text', text }] }` per the MCP spec — never thrown. This way the JSON-RPC envelope stays valid and the client gets a typed error.

**`structuredContent`:** when the tool's `outputSchema` declares a shape, the SDK requires the result to include `structuredContent` matching that shape. `whoami` returns both `content` (text fallback for clients that don't render structured) and `structuredContent` (the typed payload).

**`McpState`:** `apps/backend/src/app/mcp/server/mcp.types.ts:9-18`:

```ts
export type McpRole = 'employer' | 'candidate';

export interface McpState {
  userId: string;
  role: McpRole;
  companyId: number | null;
  prisma: PrismaClient;
  logger: Logger;
  matchExplanationService: MatchExplanationService;
  eventEmitter: EventEmitter2;
  notificationsService: NotificationsService;
}
```

`role` and `companyId` are resolved per-request by the `McpEndpointController` (see §5). `companyId` is `null` for `candidate` keys (and for `employer` keys where the user has no `employer` row, which is a config error). `matchExplanationService`, `eventEmitter`, `notificationsService` are required (not optional) and used by `apply_to_job` to mirror the web's `createApplication` flow.

**User model caveat:** the `User` model has no `candidate` field — only `candidateDescription` (1:1) and `resumes` (1:many). `hasCandidateProfile` is derived: `!!user.candidateDescription || user.resumes.length > 0`.

## 6b. Tools — employer (v2)

Nine employer-scoped tools, all registered only when `state.role === 'employer'`. They live under `apps/backend/src/app/mcp/tools/employer/`:

| File                        | Tool name           | Purpose                                                                                                                                                            |
| --------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `get-my-company.tool.ts`    | `get_my_company`    | Resolve the caller's company (uses `state.companyId`)                                                                                                              |
| `list-categories.tool.ts`   | `list_categories`   | List all job categories                                                                                                                                            |
| `list-skills.tool.ts`       | `list_skills`       | List all skills                                                                                                                                                    |
| `list-jobs.tool.ts`         | `list_jobs`         | Paginated list of the caller's own jobs (filtered by `postedById`); `{ jobs, total, page, pageSize, totalPages }`                                                  |
| `get-job.tool.ts`           | `get_job`           | Fetch one job by id; rejects if `job.companyId !== state.companyId` (returns "Forbidden" message)                                                                  |
| `create-job.tool.ts`        | `create_job`        | Create a job (auto-injects `state.companyId` + `postedById`; rejects if `state.companyId === null`)                                                                |
| `update-job.tool.ts`        | `update_job`        | Update a job; rejects if `job.postedById !== state.userId`; no companyId check                                                                                     |
| `change-job-status.tool.ts` | `change_job_status` | Change a job's status; rejects if `job.postedById !== state.userId`; no companyId check                                                                            |
| `list-applicants.tool.ts`   | `list_applicants`   | Paginated list of applicants for a job; rejects if `job.companyId !== state.companyId` AND filters by `postedById: state.userId`; supports status + search filters |

**Switchboard:** `register-employer-tools.ts` calls all nine `register*Tool(server, state)` functions. `mcp.factory.ts` calls the switchboard conditionally:

```ts
if (state.role === 'employer') {
  registerEmployerTools(server, state);
} else if (state.role === 'candidate') {
  registerCandidateTools(server, state);
}
```

Candidate keys (`state.role === 'candidate'`) take the `else if` branch — they get 8 tools (whoami + 7 candidate tools; see §6c).

**Shared Zod schemas:** `employer.types.ts` defines input shapes for tools that need them (`CreateJobInputSchema`, `UpdateJobInputSchema`, `ListJobsInputSchema`, `ListApplicantsInputSchema`, `ChangeJobStatusInputSchema`, `GetJobInputSchema`, `JobRequirementInputSchema`). Prisma enums are referenced via `z.enum(JobStatus)`, `z.enum(EmploymentType)`, `z.enum(RequirementImportance)`, `z.enum(ApplicationStatus)` — zod v4 syntax (not `z.nativeEnum`, which is deprecated).

**Ownership model — two separate axes:** tools enforce either `companyId` scoping or `postedById` scoping depending on what's appropriate. There is **no cross-company access** in any tool, but cross-user access within the same company IS allowed for read-only tools:

- **`companyId` scope** (verifies the job belongs to caller's company): `get_job`, `list_applicants`. Both reject cross-company access with `Forbidden: job does not belong to your company`.
- **`postedById` scope** (verifies the caller originally posted the job): `update_job`, `change_job_status`. Both reject with `Forbidden: only the job poster can …`. This is stricter than `companyId` scoping — it prevents one user in a company from editing another's job.
- **`postedById` filter (listing)**: `list_jobs` returns only jobs where `postedById === state.userId`, regardless of company membership.
- **Auto-injected on create**: `create_job` writes `companyId: state.companyId` and `postedById: state.userId` into the new row; the client never sets these. The handler also rejects with `Forbidden: no employer profile` if `state.companyId === null`.

**Trade-off:** the `postedById`-only checks on `update_job` and `change_job_status` mean a company with multiple users cannot have one user close another's job. An admin/manager role with broader edit rights is out of scope (see §11).

**Handler pattern:** same as `whoami` (§6) — each tool exports a pure `*Handler(state, input)` and a thin `register*Tool(server, state)` wrapper. All nine handlers are unit-tested directly (no `McpServer.callTool` available — see §6 "Why two exports").

if (state.role === 'employer') {
  registerEmployerTools(server, state);
} else if (state.role === 'candidate') {
  registerCandidateTools(server, state);
}
```

**Shared Zod schemas:** `candidate.types.ts` defines input shapes: `SearchJobsInputSchema`, `ApplyToJobInputSchema`, `ListMyApplicationsInputSchema`, `WithdrawApplicationInputSchema`, `UpdateProfileInputSchema`.

**`apply_to_job` complexity:** this is the most involved tool (187 lines). The full flow:

1. Parse + validate input (`jobId`, optional `resumeId`)
2. Look up job — reject with "Job not found" if missing, "Job is not open for applications" if not `OPEN`
3. Resolve resume — use provided `resumeId` (reject if not owned by caller), else fall back to `isDefault: true` (reject if none)
4. Check existing application — `APPLIED`/`PRE_SHORTLIST_*`/`INTERVIEW`/`OFFER`/`REJECTED` → "Already applied to this job"; `WITHDRAWN` → re-activate with new resume
5. Create or re-activate the application row
6. Fire-and-forget `MatchExplanationService.calculateExplanation` (best-effort, errors logged)
7. Determine initial status: `PRE_SHORTLIST_PENDING` if `preShortlistThreshold > 0` AND questions exist AND `matchPercentage >= threshold`; else `APPLIED`
8. Emit `job.viewed` event (best-effort, errors logged)
9. Create 2 notifications via `NotificationsService.createNotifications` (best-effort, errors logged)
10. Re-fetch with includes and return

**Known limitations (carried from v2):**

- **`ZodError` swallowed:** `inputSchema.parse()` throws inside the handler's `catch` block, returning generic "Internal error" instead of a structured `ZodError`. Carried forward from the employer tools pattern — a deliberate trade-off to keep handler signatures uniform.
- **No `$transaction`:** `apply_to_job` mutates `application`, then does `calculateExplanation`, `eventEmitter.emit`, and `notificationsService.createNotifications` — all outside a Prisma `$transaction`. If the process crashes between steps 5 and 9, the application exists but notifications may be lost. Deferred to v4+ (spec §6).
- **Race condition on concurrent apply:** two simultaneous `apply_to_job` calls for the same `(jobId, userId)` can both pass the "existing" check and create duplicate application rows. A DB unique constraint on `Application(jobId, candidateId)` + `P2002` handling would prevent this — deferred to v4+ (spec §6).

**Handler pattern:** same as whoami (§6) and employer tools (§6b) — each exports a pure `*Handler(state, input)` and a thin `register*Tool(server, state)` wrapper. All seven handlers are unit-tested directly.

`apps/backend/src/main.ts:46-59` — additive only, no existing config removed:

app.enableCors({
  origin: [
    process.env.WEB_URL || 'http://localhost:5173',
    process.env.APP_URL || 'http://localhost:3000',
  ],

  allowedHeaders: [
    'Content-Type',
    'Authorization', // ← added for Bearer
    'x-api-key', // ← added for clients that prefer this header
    'mcp-session-id', // ← added (forward-compat, even though stateless skips it)
  ],
  exposedHeaders: ['mcp-session-id'], // ← added
});
```

**Why forward-compat headers:** a future stateful mode (currently off the table) would require `Mcp-Session-Id`. The header is allowed today so flipping the config later doesn't need a CORS update. `x-api-key` is allowed for clients that prefer it over the `Authorization: Bearer` convention (opencode uses Bearer by default).

**`credentials: true`** is mandatory — opencode sends the session cookie on `/api/mcp-keys` requests. CORS preflight must allow the `Cookie` header (default).

## 11. Out of scope (v4+)

- **AI-only candidate tools** — e.g. `get_job_match_preview`, `tailor_resume_to_job`. Requires LLM integration and streaming support not yet built.
- **Messaging tools** — `send_message`, `list_threads` between candidates and employers. Requires the messaging module to be MCP-ready.
- **Pre-shortlist answering tools** — candidate-facing tools for answering pre-shortlist questions. Requires `PreShortlistModule`.
- **Resume upload** — uploading a new resume file via MCP. Requires GCS integration + file parsing pipeline.
- **One-key-per-role enforcement** — the service accepts duplicate keys for the same `(userId, role)` pair. The UI is expected to delete the old key; a DB-level unique index is deferred.
- **Stateful mode** — confirmed off the table. CORS headers for `Mcp-Session-Id` are present for forward-compat only.
- **AI / streaming** — every shipped tool is deterministic. v4+ tools that call LLMs (e.g. `summarize-resume`) will need streaming SSE or chunked responses — currently unhandled by the stateless transport.
- **Cross-company admin tools** — all employer tools scope to `state.companyId`. A superuser that can act across companies would need a separate `admin` role and a separate tool group.
- **Cross-company candidate comparison** — comparing candidates across different companies is out of scope for the current employer toolset.
- **Granular per-tool permissions** — the `permissions` JSON column currently stores a single `role`. v4+ could add per-tool scopes (e.g. `{ role: ['employer'], tools: ['read_only'] }`) and have the guard/factory consult them.
- **`McpState` cleanup** — `companyId` is always `null` for candidate keys. Could be refactored to a discriminated union or removed from the base interface.
- **DB unique constraint on `Application(jobId, candidateId)`** — a unique index + `P2002` handling would fix the race condition on concurrent `apply_to_job`. Deferred per spec §6.
